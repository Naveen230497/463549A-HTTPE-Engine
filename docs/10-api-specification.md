# API Specification Design

## Overview
The full API schema is available in `api/openapi.yaml`. This document explains the architectural reasoning behind the API design choices for the HTTPE project.

## 1. Asynchronous P2P Processing (HTTP 202 Accepted)
At 12,000 TPS, keeping HTTP connections open while waiting for database locks and Kafka consumers is dangerous and can lead to thread exhaustion (Bottleneck BN-003).
*   **Design:** The `POST /payments/p2p` endpoint does NOT wait for the transaction to fully settle. It performs fast, synchronous validation (Idempotency check, JWT validation, basic balance check, Fraud evaluation), publishes the event to Temporal/Kafka, and immediately returns a `202 Accepted` with a `PROCESSING` status.
*   **Client Experience:** The client receives the `202` response in <50ms. The client then waits for an asynchronous WebSocket push notification (from the Notification Service) to confirm the transaction is `COMPLETED` or `FAILED`.

## 2. Idempotency Keys
As outlined in `pseudocode/idempotency-handler.py`, the `X-Idempotency-Key` header is mandatory for all state-mutating requests (`POST`, `PUT`, `PATCH`). 
*   This prevents duplicate charges if the client experiences a network timeout and retries the request. 
*   If the exact same key is submitted twice, the API Gateway immediately returns the exact HTTP response (status code and body) generated by the first successful execution, fetched from Redis.

## 3. Cursor-Based Pagination
For high-volume endpoints like `GET /accounts/{account_id}/transactions`, traditional offset-based pagination (`OFFSET 10000 LIMIT 50`) is devastating to database performance. As the offset grows, the database must scan and discard thousands of rows.
*   **Design:** We implement Cursor-Based Pagination. The client provides a `cursor` (e.g., the UUIDv7 or `created_at` timestamp of the last seen record).
*   **Query:** The database executes a much faster index-range scan: `SELECT * FROM transactions WHERE created_at < :cursor ORDER BY created_at DESC LIMIT 50`.
*   **Response:** The API includes a `next_cursor` in the response payload for the client to use in the subsequent request.

## 4. Rate Limiting Strategy
Rate limiting is enforced at the Kong API Gateway layer using Redis counters.
*   **Basic Tier:** 50 requests per second.
*   **Premium Tier:** 200 requests per second.
*   **Merchant Tier:** 1,000 requests per second.
*   Limits are calculated using a Sliding Window algorithm to smoothly handle traffic spikes without cutting off legitimate burst traffic abruptly.
